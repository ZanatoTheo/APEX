1. Summary
Project Apex is a competitive evolutionary synthesis engine that produces task-specialized autonomous agents ("Agent Specs") through automated natural selection. Descended from the Protocol Wilderness design, Apex addresses the fragility of static prompt routing and procedural skill generation in multi-agent systems. The central technical bet of Project Apex is that complex, non-stationary task execution is best mastered not by hardcoding agent structures, but by running parallel subagent populations over a cryptographically verified decision ledger governed by hard safety gates, evidence-backed causal attribution, behavioral distance constraints, and hidden evaluation holdouts.

3. Goals and Non-Goals
Goals
 * Automate the generation of reliable, task-specialized agent topologies through evolutionary pressure within bounded drift envelopes.
 * Provide absolute auditability of agent execution history via cryptographically linked Merkle-DAG ledgers.
 * Enforce rigorous structural defenses against Goodharting, metric gaming, unsafe mutations, and monoculture collapse.
Non-Goals
 * No claim of absolute, unqualified zero-hallucination execution; performance is qualified by bounded error rates across named test distributions.
 * No claim of operating a literal, unconstrained free-market price discovery mechanism without explicit exchange framing.
 * No claim of handling arbitrary, unconstrained task domains outside defined operational envelopes.
 * No real-money financial deployment or live automated trading without human-in-the-loop authorization.
 * No HFT-class sub-millisecond execution latency.
4. Design Principles
 * Mechanism without defense is incomplete; every optimization loop must include structural safeguards against metric gaming.
 * Hidden evaluation must exist wherever public evaluation is optimized, managed via custodian separation to prevent contamination.
 * Mutation must be causally directed through empirical evidence links rather than unguided random search or model confidence scores.
 * Rubric criteria must remain stable within a defined generation window to allow populations to adapt without shifting targets.
 * Hard safety gates are binary, non-negotiable, and never traded off against soft optimization criteria, subject only to multi-party emergency patching.
 * Centralized consensus axioms are treated strictly as heuristic suggestions rather than mandatory central plans.
 * Population diversity must be actively maintained via versioned composite behavioral distance constraints to prevent UCB1 monoculture collapse.
 * State transitions must be deterministically serializable using canonical JSON rules and validated via Merkle-DAG verification trees.
 * Escalation to heavy macro-reasoning models must be triggered by Median Absolute Deviation (MAD) entropy spikes or runtime execution deadlocks.
 * Agent specs deployed to production must carry explicit, quantified robustness bounds defining performance within a verified operational envelope.

6. Subagent Model
Swarm subagents are lightweight, stateless functional containers instantiated dynamically by the Swarm Orchestrator. They execute defined state machine routines, invoke permitted tools, and log their actions to the decision ledger before terminating or yielding.
Comparison of Execution Actors
| Feature | Swarm Subagent | Meta Muse Code | Meta Muse Spark |
|---|---|---|---|
| Primary Role | Execute tasks and generate execution trails. | Mutate, patch, and compile subagent units across scopes. | Provide directed causal search and macro-reasoning. |
| Execution Speed | High throughput, low latency. | Moderate (triggered on failure/mutation). | Low throughput, high compute cost. |
| Isolation Level | Sandboxed Docker container with strict network policy. | Host-level AST parsing with sandboxed test compilation. | API-level model invocation. |
| State Retention | Transient per task execution; ledger-backed. | Stateless utility actor. | Stateless reasoning actor. |
7. Execution and Topology
Subagents execute tasks via deterministic state machines driven by explicit prompt axioms, tool call signatures, and routing logic.
 * Topology Representation: A subagent topology is represented as a hybrid structure combining an explicit state-transition graph (JSON configuration) and executable execution scripts (Python).
 * Execution Flow: The subagent ingests state, evaluates the current node in the state graph, executes the assigned tool or reasoning step, logs the action to the ledger, and transitions based on output validation.
> Open Point: The precise formalization of topology representation (pure graph configuration vs. dynamic script synthesis) remains an open design choice during early implementation.
> 
8. Decision Ledger
The Decision Ledger is implemented as an append-only, cryptographic Merkle-DAG supporting parallel branching and deterministic merging.
Branching, Merging, and Canonical Rules
 * Branching: When a subagent forks into mutation variants, a child block references the parent hash and assigns a unique branch_id using a Lamport logical clock.
 * Merging & Conflict Resolution: Conflicting state reductions from parallel branches must satisfy commutative monoid rules. Merge conflicts are resolved deterministically by selecting the state branch with the highest verified hidden fitness score.
 * Canonical Serialization: All dictionary keys are sorted lexicographically, floats are normalized to 8 decimal places, and whitespace is stripped prior to SHA-256 hashing.
9. Fitness and Evaluation
Evaluation is layered hierarchically to ensure structural safety and resilience against metric gaming.
Layered Evaluation Architecture
 * L0 Hard Gates: Binary pass/fail criteria (1 or 0). Evaluated first; failure results in immediate disqualification.
 * L1 Soft Criteria: Weighted optimization targets (speed, token cost, accuracy, style adherence).
 * L2 Robustness Criteria: Multi-distribution stress testing assessing performance degradation under input drift.
 * L3 Diversity and Coverage: Population-level penalties using a versioned composite behavioral distance metric D(A_1, A_2) = w_1 d_{\text{tool}} + w_2 d_{\text{path}} + w_3 d_{\text{emb}} applied during survivor selection.
 * L4 Meta-Signals: Tracking divergence between public scores and custodian-managed hidden holdout scores.
10. Mutation and Pruning
When a subagent fails execution thresholds or triggers an entropy spike, Meta Muse Code initiates a mutation cycle across three distinct units:
 * Code Unit (Python AST): Patched via AST transformation with syntax validation.
 * Graph Config (JSON State Machine): Patched via schema-validated JSON diffs.
 * Prompt Axioms (Semantic Strings): Patched via semantic diff injection.
Each unit maintains individual validation checks and independent rollback capabilities. Every mutation must cite an empirical evidence link in the Causal Attribution Log. KL divergence monitoring (D_{KL}(P \parallel Q)) ensures output distributions do not exceed stability thresholds.
11. Escalation and Entropy Triggers
To minimize expensive API calls while maintaining system stability, escalation is governed by rigorous mathematical triggers:
 * MAD Entropy Baseline: Predictive entropy H(X) is monitored using Median Absolute Deviation (MAD) against a rolling baseline, eliminating skew vulnerability. When entropy spikes, execution escalates to Meta Muse Spark.
 * Runtime Deadlock Detection: Replaces static SCC graph analysis with a runtime wait-for graph combined with strict execution timeouts to catch active execution deadlocks.
 * Signal Watcher: Lightweight observer agents sample peer logs at randomized intervals to flag systemic error propagation.
12. Rubric Windows and Governance
 * Rubric Windows (N = 50 Generations): Evaluation criteria, soft weights, and baseline benchmarks are frozen for N generations.
 * Operator Governance: Meta Muse Spark accumulates proposed rubric recalibrations during the window. At the window boundary, the operator reviews proposals and may apply at most one bounded, logged revision.
 * Emergency Gate Patch Protocol: Hard gates (L0) are immutable during normal operation but can be updated via a versioned patch requiring cryptographic multi-party operator approval logged directly to the Genesis block.
13. Agent Spec Freezing and Deployment
When an evolutionary lineage achieves rigorous verification, it transitions to a permanent Agent Spec.
 * Verification Threshold: Achievement of \ge 99.9\% success across a standardized benchmark suite comprising at least 1,000 diverse test iterations spanning 5 named dynamic distributions.
 * Operational Envelope: Deployed specs carry quantified robustness bounds defining performance degradation limits under input drift.
14. Tool Registry and Sandbox
 * Tool Entry Schema: Defines tool name, input schema, output specification, permission level, and timeout limits.
 * Sandbox Specification: Subagents execute within ephemeral, rootless Docker containers with custom seccomp profiles, dropped kernel privileges, and zero network egress by default (routing exclusively through an authenticated local API proxy with strict egress allowlists).
15. Safety, Security, and Compliance
Threat Model Matrix
| Threat | Mechanism | Defense |
|---|---|---|
| Reward Hacking | Subagents exploit loophole metrics to artificially inflate public scores. | Custodian-managed hidden holdout task sets; L0 hard gates. |
| Public-Score Gaming | Overfitting to known training evaluation questions. | Dynamic rotation of hidden holdout tasks and L4 divergence tracking. |
| Monoculture Collapse | UCB1 convergence eliminates diverse exploratory behaviors. | Versioned composite behavioral distance constraints (\epsilon) during survivor selection. |
| Silent Model Swap | Unauthorized substitution of model backends during execution. | Cryptographic verification of model endpoint signatures and L0 hard gates. |
| Prompt Injection | Malicious inputs injected via external tool outputs. | Strict output sanitization and rootless containerization with seccomp profiles. |
| Ledger Tampering | Unauthorized modification of historical execution logs. | Cryptographic hash-chained Merkle-DAG architecture with branch validation. |
| Sandbox Escape | Malicious code breaking out of container isolation. | Rootless Docker, custom seccomp profiles, dropped capabilities, and zero network access. |
| Causal Overfitting | Over-optimizing mutations to anomalous historical noise. | KL divergence monitoring and empirical evidence-linked attribution logs. |

17. Roadmap
Phase 1: Hackathon MVP (Deliverable in 10-Day Sprint)
 * Append-only Merkle-DAG Decision Ledger with canonical JSON serialization and Lamport clocks.
 * Swarm Orchestrator and rootless Docker sandbox pool with custom seccomp profiles.
 * L0 Hard Gates and basic L1 Soft Criteria evaluation engine.
 * Scripted and human-reviewed mutation workflow (deferring automated self-compiling loops to Phase 2).
Phase 2: Post-Hackathon Hardening
 * Custodian-managed hidden holdout evaluation splits.
 * Causal Attribution Log and empirical evidence linking.
 * Versioned composite behavioral distance constraints on survivor selection.
 * Rubric windows and emergency gate patch protocols.
Phase 3: Advanced Ecosystem Integration
 * Full deployment of SAM 3.1 visual parsing pipelines.
 * Signal Watcher cross-agent learning loops.
 * Production hardening and multi-distribution stress testing suites.
18. Open Points
 * Topology Representation: Whether subagent topologies should be strictly graph-configured state machines or fully synthesized Python scripts.
 * Distance Metric Weights (w_1, w_2, w_3): Empirical calibration of tool profile vs. state path vs. embedding distance weights in the behavioral signature.
 * MAD Entropy Calibration: Empirical tuning parameters for the MAD entropy escalation threshold across different task domains.
 * Window Length (N): Determining the optimal generation count for Rubric Windows under rapid vs. slow task distribution shifts.
 * Agent Spec Portability: Ensuring frozen Agent Specs can execute reliably across different underlying model version updates.
 * SAM 3.1 Output Evaluation: Defining standardized validation metrics for visual layout and workflow parsing outputs.
19. One-Line Definition
Project Apex is a competitive evolutionary synthesis engine that generates verified, task-specialized autonomous agents by running parallel subagent populations over an immutable decision ledger governed by hard safety gates, evidence-backed causal attribution, and custodian-managed hidden holdouts.
