## Phase 4: Ledger & serialization (R6, R7, R8, R10, R14)

### C-25 · §8 Branching · R7
- **Original (orig l.125):** "…a child block references the parent hash and assigns a unique branch_id using a Lamport logical clock."
- **New (revised after the Phase 4 review):**
  - Branching: "Each subagent's history is its own branch. When a child is created, its first block references its parent's latest block by hash. Its branch_id is SHA-256(that parent block_hash ‖ child agent_id), computed before the block is built and carried by every later block on the branch. Seeds fork from Genesis the same way. Genesis and run-level events (batch sampling, selection, gate versions) form the root branch, with branch_id "root"."
  - New bullet, Ordering: "the orchestrator is the single writer of the ledger (MVP: one process appending under a lock); workers hand their transitions to it. Each block's lamport_clock = max(parent's lamport_clock, the writer's last value) + 1."
- **Why:** Lamport clocks order events; they don't generate unique IDs. My first draft (branch_id = hash of the branch's own first block) was circular, because branch_id is a hashed field of that block; the reviewer caught it. The clock also needed an update rule and a single writer.
- **Status:** PENDING

### C-26 · §8 Canonical Serialization · R8
- **Original (orig l.127):** "All dictionary keys are sorted lexicographically, floats are normalized to 8 decimal places, and whitespace is stripped prior to SHA-256 hashing."
- **New:** "Blocks are first validated against the §16 schema as I-JSON (no duplicate keys, finite numbers, integers within ±2^53), then serialized with the JSON Canonicalization Scheme (RFC 8785: sorted keys, no insignificant whitespace, standard number formatting) and hashed with SHA-256. (The I-JSON clause was added after the Phase 4 review; RFC 8785 is only defined for I-JSON input.) block_hash = SHA-256 of the canonical form of the block without its block_hash field. Whitespace inside string values is preserved."
- **Why:** stripping whitespace would corrupt string content (code, prompts), and rounding to 8 places is ad hoc. RFC 8785 is a standard with existing libraries. The doc also never said which fields are hashed.
- **Status:** PENDING

### C-27 · §8 new bullets: Structure, Genesis, Verification · R6, R8
- **Original:** none.
- **New:**
  - "Structure: the ledger is a Merkle DAG in the Git sense: each block is addressed by the hash of its content, which includes its parent's hash. With no merging, every block has exactly one parent, so the ledger forms a tree rooted at the Genesis block. Blocks are identified by block_hash; height (distance from Genesis) is not unique across branches."
  - "Genesis: the Genesis block's state_transitions record, by result_hash, the run config, the L0 gate definition (gate version 1) and the task-corpus manifest (public and hidden), so a changed config, gate or holdout is detectable."
  - "Verification: recompute every block_hash. Check that every parent_hash refers to an existing block, that height = parent height + 1 and lamport_clock > the parent's, and that every result_hash matches its stored content. This only detects inconsistent edits. To detect a full rewrite with recomputed hashes, the head hash of every branch is published outside the ledger at the end of each generation (MVP: in the run report and on the operator's console), and verification compares against the published heads."
- **Why:** this fixes the ambiguous block_index (R6) and states how tampering is detected. The corpus-manifest hash protects the static holdout.
  - *Revised after the Phase 4 review:*
    - Genesis contents are recorded as ordinary state_transitions, so no schema change is needed, and the gate is recorded by definition hash, not just a version number.
    - Verification checks height and clock.
    - Published heads are needed because recomputing hashes alone can't detect a full rewrite.
  - **Open for you:** the reviewer considers "Merkle DAG" a misnomer for a single-parent tree. I kept the term, since IPFS/Git use it for any hash-linked structure and renaming touches about 6 places. Say if you want it renamed to "hash-linked tree".
- **Status:** PENDING

### C-33 · §11 MAD Entropy Baseline · R11
- **Original (orig l.144):** "Predictive entropy H(X) is monitored using Median Absolute Deviation (MAD) against a rolling baseline, eliminating skew vulnerability. When entropy spikes, execution escalates to Meta Muse Spark."
- **New:** "Predictive entropy H(X) is estimated by sample disagreement: the step is run n = 5 times, and H(X) is the Shannon entropy of the distribution of distinct normalized outputs (token log-probabilities are used instead where the model API provides them). The threshold is a default to be calibrated (§18)."
- **Why:** the entropy source was undefined, and many APIs return no log-probabilities. The trigger needs a formula. "Eliminating skew vulnerability" overclaimed; MAD reduces sensitivity to outliers. Phase 2 scope, per C-17.
