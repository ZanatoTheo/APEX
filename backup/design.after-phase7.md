# Project Apex — Main Design Document
- Status: Active MVP Sprint
- Version: 1.2.0 (draft; changes pending approval, see CHANGES.md)
- Date: 2026-10-31
## 1. Summary
Project Apex is a competitive evolutionary synthesis engine that produces task-specialized autonomous agents ("Agent Specs") through automated natural selection. Descended from the Protocol Wilderness design, Apex addresses the fragility of static prompt routing and procedural skill generation in multi-agent systems. The central technical bet of Project Apex is that complex, non-stationary task execution is best mastered not by hardcoding agent structures, but by running parallel subagent populations over a cryptographically verified decision ledger governed by hard safety gates, evidence-backed causal attribution, behavioral distance constraints, and hidden evaluation holdouts. The MVP targets one task family: repairing small Python repositories that have failing unit tests, where public tests drive selection and hidden tests form the holdout (§9.1).

Sections 1, 3, 4 and 19 describe the full system. What the MVP actually delivers is set by §17 Phase 1, and MVP-specific limits are marked throughout.
## 2. Core Concepts
| Term | Definition |
|---|---|
| Swarm Subagent | A lightweight, isolated execution instance operating within a parallel swarm to execute tasks. |
| Meta Muse Spark | The macro-reasoning model responsible for directed causal search, policy adjustment, and consensus axiom suggestions (Phase 2). |
| Meta Muse Code | The code-generation model responsible for generating mutation proposals (one mutation unit per proposal) and, from Phase 2, AST parsing, patching and script compilation. |
| SAM 3.1 | The visual parsing model used to convert diagrams, UI states, and visual workflows into structured vector embeddings (Phase 3). |

| Agent Spec | A production-ready, verified autonomous agent state machine and prompt axiom package frozen after passing rigorous stress thresholds. |
| Causal Attribution Log | A parallel ledger recording empirical evidence links for every mutation proposal (MVP: the hash of the motivating failing trace; regression diffs and replay traces from Phase 2). |
| Rubric Window | A fixed duration of N generations during which evaluation criteria are frozen against live operator updates. |

| Custodian | The role that holds the hidden holdout and alone can read or rotate it. In the MVP it is the Evaluation Engine process (static split); from Phase 2 it is a separate service or person. |
| Escalation Event | A state trigger (MAD entropy spike, runtime execution deadlock, or a Signal Watcher flag from Phase 3) forcing transfer of control to Meta Muse Spark (Phase 2). |
| Mutation Proposal | A structured patch to exactly one mutation unit (one in-place edit), generated by Meta Muse Code and citing a causal attribution entry. |
| Behavioral Signature | A versioned composite vector (tool profile + state path Jaccard + output embedding) measuring subagent divergence (Phase 2; d_path is the Jaccard distance between visited-node sets). |
| Generation | One iteration of the evolution loop: evaluate the population on a batch of public tasks, select survivors, and produce children (§10). |
| Lineage | All subagents descending from one root ancestor, identified by lineage_id; the arm used by UCB1 parent selection. |
| Child | A copy of a parent subagent with one in-place edit (add, modify or remove) to a single mutation unit. The edit changes the copy's existing content rather than appending to it. The child gets its own agent_id and ledger branch; the parent is unchanged. |
| Genesis | The root block of the ledger; records the run config, L0 gate definition and corpus manifest by hash (§8). |
| Batch | The K public tasks sampled for one generation; every member is evaluated on the same batch (§10). |
| UCB1 | Upper Confidence Bound bandit rule used to pick parent lineages, balancing high mean reward against few visits (§10). |
| Canary Task | A fixed task with a known score, run to detect silent model changes (Phase 2, §15). |
| Seed | A generation-0 subagent; the root of its own lineage (§10). |
| Survivor | A member kept by selection in step 3 of a generation (§10). |
| Task Run | One subagent executing one task in one sandbox, bounded by token_budget and timeout (§10). |
| Held-out Task | A task never used in batches, run only by the final survivors at the end of the run (§9.1). |
| Mutation Unit | One editable part of a subagent: Graph Config, Prompt Axioms, or (Phase 2) Code (§10). |
| Graph Config | The JSON state machine of a subagent: nodes, transitions and step cap (§16). |
| Prompt Axiom | One instruction string in a subagent's ordered axiom list, referenced by index from llm nodes (§16). |
## 3. Goals and Non-Goals
### Goals
 * Automate the generation of reliable, task-specialized agent topologies through evolutionary pressure within bounded drift envelopes.
 * Provide absolute auditability of agent execution history via cryptographically linked Merkle-DAG ledgers.
 * Enforce rigorous structural defenses against Goodharting, metric gaming, unsafe mutations, and monoculture collapse.
 * Show, in the MVP, that an automated mutate → evaluate → select loop improves agents on the Python bug-fix task family, measured on the hidden holdout.
### Non-Goals
 * No claim of absolute, unqualified zero-hallucination execution; performance is qualified by bounded error rates across named test distributions.
 * No claim of operating a literal, unconstrained free-market price discovery mechanism without explicit exchange framing.
 * No claim of handling arbitrary, unconstrained task domains outside defined operational envelopes; the MVP envelope is the Python bug-fix task family (§9.1).
 * No real-money financial deployment or live automated trading without human-in-the-loop authorization.
 * No HFT-class sub-millisecond execution latency.
## 4. Design Principles
 * Mechanism without defense is incomplete; every optimization loop must include structural safeguards against metric gaming.
 * Hidden evaluation must exist wherever public evaluation is optimized. It is readable only by the Evaluation Engine (static split in the MVP, custodian separation in Phase 2) and is never used as a selection signal.
 * Mutation must be causally directed through empirical evidence links rather than unguided random search or model confidence scores.
 * Rubric criteria must remain stable within a defined generation window to allow populations to adapt without shifting targets.
 * Hard safety gates are binary, non-negotiable, and never traded off against soft optimization criteria, subject only to multi-party emergency patching (Phase 2).
 * Centralized consensus axioms are treated strictly as heuristic suggestions rather than mandatory central plans.
 * Population diversity must be actively maintained via versioned composite behavioral distance constraints to prevent UCB1 monoculture collapse (Phase 2; the MVP relies on UCB1 exploration only and accepts the residual risk, see §15).
 * State transitions must be deterministically serializable using canonical JSON rules and validated via Merkle-DAG verification trees.
 * Escalation to heavy macro-reasoning models must be triggered by Median Absolute Deviation (MAD) entropy spikes or runtime execution deadlocks (Phase 2; the MVP uses hard execution timeouts only, see §11).
 * Agent specs deployed to production must carry explicit, quantified robustness bounds defining performance within a verified operational envelope.

## 6. Subagent Model
Swarm subagents are lightweight, stateless functional containers instantiated dynamically by the Swarm Orchestrator. They execute defined state machine routines, invoke permitted tools, and log their actions to the decision ledger through the orchestrator, its single writer (§8), before terminating or yielding.
### Comparison of Execution Actors
| Feature | Swarm Subagent | Meta Muse Code | Meta Muse Spark |
|---|---|---|---|
| Primary Role | Execute tasks and generate execution trails. | Propose one-unit mutations (MVP: graph config and prompt axioms; code patching and compilation from Phase 2). | Provide directed causal search and macro-reasoning. |
| Execution Speed | High throughput, low latency. | Moderate (one call per child, every generation). | Low throughput, high compute cost. |
| Isolation Level | Sandboxed Docker container with strict network policy. | API-level model invocation. Its output is treated as untrusted: graph-config patches are validated against the graph schema and prompt-axiom edits against the axiom-edit format (§16) before use, and any Python it produces (code_ast, Phase 2) is parsed and compiled only inside the sandbox pool. | API-level model invocation. |
| State Retention | Transient per task execution; ledger-backed. | Stateless utility actor. | Stateless reasoning actor. |
## 7. Execution and Topology
Subagents execute tasks via state machines driven by explicit prompt axioms, tool call signatures, and routing logic. Transitions are deterministic given each step's output, but model outputs are not. Every model request and response, and every tool call and result, is therefore stored as one record in a content-addressed store next to the ledger, referenced by result_hash. Replays reuse the stored outputs instead of calling models again. They reproduce the transitions and outputs, not the block bytes, because timestamps and clocks differ.
 * Topology Representation: A subagent topology is represented as a hybrid structure combining an explicit state-transition graph (JSON configuration) and executable execution scripts (Python). In the MVP the topology is a Graph Config (§16) plus prompt axioms only; Python scripts arrive with the code_ast unit in Phase 2.
 * Execution Flow: The subagent ingests state, evaluates the current node in the state graph, executes the assigned tool or reasoning step, logs the action to the ledger, and transitions based on output validation.
> Open Point: The precise formalization of topology representation (pure graph configuration vs. dynamic script synthesis) remains an open design choice during early implementation.

## 8. Decision Ledger
The Decision Ledger is implemented as an append-only, cryptographic Merkle-DAG supporting parallel branching. Merging is out of scope for the MVP (§18).
### Branching and Canonical Rules
 * Branching: Each subagent's history is its own branch. When a child is created, its first block references its parent's latest block by hash. Its branch_id is SHA-256(that parent block_hash ‖ child agent_id), computed before the block is built and carried by every later block on the branch. Seeds fork from Genesis the same way. Genesis and run-level events (batch sampling, selection, gate versions) form the root branch, with branch_id "root".
 * Ordering: the orchestrator is the single writer of the ledger (MVP: one process appending under a lock); workers hand their transitions to it. Each block's lamport_clock = max(parent's lamport_clock, the writer's last value) + 1.
 * No Merging: lineages only fork. Survivors are chosen by selection (§10), not merged, so every block has exactly one parent. The hidden score plays no part in the ledger.
 * Canonical Serialization: Blocks are first validated against the §16 schema as I-JSON (no duplicate keys, finite numbers, integers within ±2^53), then serialized with the JSON Canonicalization Scheme (RFC 8785: sorted keys, no insignificant whitespace, standard number formatting) and hashed with SHA-256. block_hash = SHA-256 of the canonical form of the block without its block_hash field. Whitespace inside string values is preserved.
 * Structure: the ledger is a Merkle DAG in the Git sense: each block is addressed by the hash of its content, which includes its parent's hash. With no merging, every block has exactly one parent, so the ledger forms a tree rooted at the Genesis block. Blocks are identified by block_hash; height (distance from Genesis) is not unique across branches.
 * Genesis: the Genesis block's state_transitions record, by result_hash, the run config, the L0 gate definition (gate version 1) and the task-corpus manifest (public and hidden), so a changed config, gate or holdout is detectable.
 * Verification: recompute every block_hash. Check that every parent_hash refers to an existing block, that height = parent height + 1 and lamport_clock > the parent's, and that every result_hash matches its stored content. This only detects inconsistent edits. To detect a full rewrite with recomputed hashes, the head hash of every branch is published outside the ledger at the end of each generation (MVP: in the run report and on the operator's console), and verification compares against the published heads.
## 9. Fitness and Evaluation
Evaluation is layered hierarchically to ensure structural safety and resilience against metric gaming.
### Layered Evaluation Architecture
 * L0 Hard Gates: Binary pass/fail criteria (1 or 0). Evaluated first; failure results in immediate disqualification. MVP gates: no sandbox violation, no network access outside the allowlisting proxy (§14), the patch applies cleanly and leaves test files untouched, and the run finishes within its timeout and token budget.
 * L1 Soft Criteria: A weighted score in [0,1]: L1 = 0.7·pass_rate + 0.2·(1 − tokens/token_budget) + 0.1·(1 − latency/timeout), each term clamped to [0,1], where pass_rate is the fraction of public tests passed over the generation's batch. Weights are defaults, frozen per rubric window. Ties are broken by lower token cost, then by the lexicographically lower block hash.
 * L2 Robustness Criteria: Multi-distribution stress testing assessing performance degradation under input drift (Phase 3).
 * L3 Diversity and Coverage: Population-level penalties using a versioned composite behavioral distance metric D(A₁, A₂) = w₁·d_tool + w₂·d_path + w₃·d_emb applied during survivor selection (Phase 2).
 * L4 Meta-Signals: Tracking divergence between public scores and hidden holdout scores (divergence = public − hidden pass rate). This and Agent Spec freezing (§13) are the only uses of the hidden score.
### 9.1 MVP Task Family: Python Bug-Fix
 * Task: a small Python repository snapshot with a seeded bug and failing public unit tests. The subagent must make the public tests pass without editing them.
 * Tools: read_file, run_tests (public tests only), write_patch (§14).
 * Public score: L1 over the generation's batch of public tasks.
 * Hidden holdout: hidden tests for every public task, plus a separate set of held-out tasks. Hidden tests are never mounted into a subagent's sandbox and never shown to the mutation model. The Evaluation Engine runs the hidden tests of each batch task against the subagent's final patch in a separate sandbox after the subagent finishes, which needs no extra model calls. The held-out tasks are run once, by the final survivors, at the end of the run.
 * Distributions: the MVP covers 2 (off-by-one, type errors), with about 30 public and 10 held-out tasks. Phase 3 adds API misuse, edge cases and logic inversion.
## 10. Evolution Loop, Mutation and Pruning
The engine evolves a fixed-size population in discrete generations, using an elitist (μ+λ) scheme with UCB1 parent selection. The defaults below are set in config.
 * Population: P = 8 subagents (μ = 4 survivors, λ = 4 children).
 * Generation 0: the population is P seed agents (seed topologies, or a baseline plus P − 1 single mutations of it). Each seed is the root of its own lineage.
 * Generation g:
   1. Sample a fresh batch of K = 10 public tasks, used for every member of the population in this generation.
   2. Evaluate every member (§9). L0 failures are disqualified; the rest are ranked by L1.
   3. Keep the top μ as survivors. Parents compete with their children (elitism).
   4. Pick λ parents by UCB1 over the lineages that have survivors, with replacement. Within a lineage, the parent is its best-ranked survivor.
   5. Produce each child by mutating its parent once (see Mutation).
   6. Append every evaluation, selection and mutation to the Decision Ledger.
 * UCB1: arm = lineage; one visit = one child produced from that lineage; reward = the child's L1 in [0,1], or 0 if it fails L0; c = √2. A lineage's score is mean_reward + c·√(ln N / n), where N is the total number of visits and n is the lineage's visits. A lineage with no visits yet is picked first. Rewards are credited when the child is evaluated in the next generation's step 2, so step 4 uses the rewards credited so far.
 * Too few survivors: if only s < μ members pass L0, all s survive and step 4 picks P − s parents instead of λ, refilling the population to P. If none pass, the generation is rolled back to the previous survivors and re-run on a new batch; the rollback counts toward G_max. If none of the generation-0 seeds pass, there are no previous survivors: the run stops and reports the seeds as failing L0.
 * Stopping: the run ends after G_max = 10 generations or when the token budget (budget.tokens_total minus budget.holdout_reserve) is spent, whichever comes first.
 * Budget: each task run is capped by token_budget (default 50,000 tokens) and timeout (default 300 s), the values L1 normalizes against; a run that exceeds either is stopped and fails L0. Each run of the engine is capped by budget.tokens_total (default 20 M tokens, covering all model calls) and budget.max_concurrent_sandboxes (default 8). budget.holdout_reserve (default 2 M tokens) of the total is kept back for the final held-out runs, so the reported result cannot be starved. With the defaults, one engine run makes at most G_max × P × K = 800 task runs, 40 mutation calls normally (at most 77 with refills and generation-0 seeding), and μ × 10 = 40 held-out task runs. Worst-case use exceeds 20 M tokens, so tokens_total is the binding cap. Phase 2 additions, such as canaries and entropy sampling, are budgeted when they are added.
 * The hidden score is never an input to steps 2–4.
### Mutation
 * A child is a copy of its parent with one in-place edit to exactly one mutation unit. The edit may add, modify or remove content. It changes what is there rather than appending to it, so specifications do not accumulate contradictory definitions across generations. The parent itself is unchanged and keeps competing (elitism).
 * Every child is produced by mutation, every generation. The edit is guided by the parent's failing public-test traces, and the proposal cites the ledger hash of the trace that motivated it in the Causal Attribution Log. If the parent passed every task in the batch, the edit is guided instead by its most expensive trace (highest token use) and aims at cost.
 * Mutation units:
   * Graph Config (JSON State Machine): Patched via schema-validated JSON diffs. (MVP)
   * Prompt Axioms (Semantic Strings): Patched via semantic diff injection. (MVP)
   * Code Unit (Python AST): Patched via AST transformation with syntax validation. (Phase 2)

Each unit maintains individual validation checks and independent rollback capabilities. Every mutation must cite an empirical evidence link in the Causal Attribution Log. Drift check (Phase 2): a child's tool-call distribution P is compared with its parent's Q via D_KL(P ‖ Q). Both are measured on the same generation's batch (the parent is re-evaluated every generation anyway) and add-one smoothed over the tool set, so the divergence is always finite. Children above a configured stability threshold (§18) are flagged in the ledger.
### Pruning
 * Members not kept as survivors are marked pruned, or disqualified on L0 failure. Their ledger history is kept.
## 11. Escalation and Entropy Triggers
Scope: Phase 2 and later. The MVP has no escalation to Meta Muse Spark; it relies on hard execution timeouts only.
To minimize expensive API calls while maintaining system stability, escalation is governed by rigorous mathematical triggers:
 * MAD Entropy Baseline: Predictive entropy H(X) of a model step is estimated by sample disagreement. Only the model call is re-sampled (n = 5, with the tokens counted against token_budget); tools are not re-executed. H(X) is the Shannon entropy of the distribution of distinct outputs, where an output is the chosen action (tool name and arguments) or, for text, the whitespace-normalized text. With n = 5, H(X) takes only 7 values, so the signal is coarse. H(X) is compared with a rolling baseline of the last 50 executions of the same state-machine node, using the Median Absolute Deviation: when (H(X) − median) / (1.4826 · max(MAD, 0.1 nats)) > 3.5, execution escalates to Meta Muse Spark. The floor on MAD avoids dividing by zero for deterministic steps. Token log-probabilities, where an API provides them, are a different quantity and would need their own baseline. n, the window, the floor and the threshold are defaults to be calibrated (§18).
 * Runtime Deadlock Detection: Replaces static SCC graph analysis with a runtime wait-for graph combined with strict execution timeouts to catch active execution deadlocks.
 * Signal Watcher: Lightweight observer agents sample peer logs at randomized intervals to flag systemic error propagation (Phase 3). Its cross-agent learning signals are logged only and are not fed into mutation until behavioral distance constraints are active, so it cannot speed up monoculture collapse.
## 12. Rubric Windows and Governance
 * Rubric Windows (default N = 50 generations): Evaluation criteria, soft weights, and baseline benchmarks are frozen for N generations. The MVP run (G_max = 10) is a single window.
 * Operator Governance: Meta Muse Spark accumulates proposed rubric recalibrations during the window. At the window boundary, the operator reviews proposals and may apply at most one bounded, logged revision. (Phase 2; the MVP run is a single window with no recalibration.)
 * Emergency Gate Patch Protocol (Phase 2; in the MVP the L0 gates are fixed for the run): Hard gates (L0) are immutable during normal operation but can be updated via a versioned patch requiring cryptographic multi-party operator approval. The approved patch is appended to the root branch as a gate-version block that records the new gate definition by hash. The Genesis block records gate version 1 and is never modified; the current gate version is the latest gate-version block on the root branch.
## 13. Agent Spec Freezing and Deployment
When an evolutionary lineage achieves rigorous verification, it transitions to a permanent Agent Spec.
 * Verification Threshold: a lineage is frozen when, on the hidden holdout, the exact (Clopper–Pearson) one-sided 95% lower bound of its success rate is at least the target p_min on every named task distribution (§9.1). Each held-out task counts once, so the bound is over distinct tasks drawn from the distribution, not over repeated runs of the same tasks. With zero failures this needs about 3 / (1 − p_min) distinct tasks per distribution: about 3,000 for p_min = 99.9%. (The earlier criterion of ≥ 99.9% over 1,000 runs allowed one failure and bounds the failure rate only at about 0.5%.)
 * MVP: the held-out task set (about 10 tasks) is far too small for this, so the MVP freezes no Agent Specs; it reports each final survivor's held-out success rate with its 95% interval.
 * Operational Envelope: Deployed specs carry quantified robustness bounds defining performance degradation limits under input drift.
## 14. Tool Registry and Sandbox
 * Tool Entry Schema: Defines tool name, input schema, output specification, permission level, timeout limits, and denied paths (§16).
 * MVP Tool Set: read_file, run_tests (runs public tests only) and write_patch (rejects any change under the task's test directories).
 * Sandbox Specification: Subagents execute within ephemeral, rootless Docker containers with custom seccomp profiles, dropped kernel privileges, and zero network egress by default (routing exclusively through an authenticated local API proxy with strict egress allowlists).
## 15. Safety, Security, and Compliance
### Threat Model Matrix
| Threat | Mechanism | Defense |
|---|---|---|
| Reward Hacking | Subagents exploit loophole metrics to artificially inflate public scores. | Hidden holdout readable only by the Evaluation Engine (static in the MVP, custodian-managed in Phase 2); test files cannot be modified by subagents; L0 hard gates. |
| Public-Score Gaming | Overfitting to known training evaluation questions. | A fresh public batch every generation; L4 divergence tracking; hidden holdout rotation (Phase 2). |
| Monoculture Collapse | UCB1 convergence eliminates diverse exploratory behaviors. | UCB1 exploration across lineages (MVP); versioned composite behavioral distance constraints (ε) during survivor selection (Phase 2). Residual MVP risk: the population can converge on one lineage within G_max. |
| Silent Model Swap | Unauthorized substitution of model backends during execution. | Model IDs pinned in the run config and checked against the model ID reported in every API response, which catches misconfiguration and provider-side alias changes but not an endpoint that echoes the pinned ID; canary tasks with known scores, flagging shifts beyond a configured threshold (Phase 2); L0 hard gates. (Model APIs generally do not sign responses, so cryptographic endpoint verification is not available.) |
| Prompt Injection | Malicious inputs injected via external tool outputs. | Tool outputs are passed to models as clearly delimited data, and prompts instruct models to treat them as data, not instructions; this reduces injection but does not prevent it. Tools are permission-scoped (write_patch cannot touch tests), and task containers have no network access other than the allowlisting proxy (§14). Containers limit the damage of a successful injection but do not prevent it. |
| Ledger Tampering | Unauthorized modification of historical execution logs. | Hash-linked ledger verified as in §8, with branch head hashes published outside the ledger every generation so that rewrites are detectable. |
| Sandbox Escape | Malicious code breaking out of container isolation. | Rootless Docker, custom seccomp profiles, dropped capabilities, and no network access other than the allowlisting proxy (§14). |
| Causal Overfitting | Over-optimizing mutations to anomalous historical noise. | Each mutation cites a concrete failing trace, and children are re-evaluated on a fresh batch every generation, so fixes fitted to one anomalous trace tend not to survive selection (with K = 10 tasks this filter is noisy); regression-diff evidence and the KL drift check (Phase 2). |

## 17. Roadmap
### Phase 1: Hackathon MVP (Deliverable in 10-Day Sprint)
 * Append-only Merkle-DAG Decision Ledger (single-parent blocks, no merging) with canonical JSON serialization and Lamport clocks.
 * Swarm Orchestrator and rootless Docker sandbox pool with custom seccomp profiles.
 * Python bug-fix task corpus: 2 distributions (off-by-one, type errors), about 30 public and 10 held-out tasks; tools read_file, run_tests, write_patch (§9.1).
 * L0 Hard Gates and L1 Soft Criteria evaluation engine, with a static hidden holdout readable only by the Evaluation Engine.
 * Automated (μ+λ) evolution loop with UCB1 parent selection and trace-guided mutation of graph_config and prompt_axiom units (§10).
 * Stub Causal Attribution Log: each mutation proposal cites the ledger hash of the failing trace that motivated it.
 * Run report: final survivors' held-out success rates with 95% intervals, and the branch head hashes published each generation (§8, §13).
### Phase 2: Post-Hackathon Hardening
 * Custodian-managed hidden holdouts with rotation.
 * Regression-diff and replay-trace evidence in the Causal Attribution Log.
 * code_ast mutation unit (Python AST patching).
 * Versioned composite behavioral distance constraints on survivor selection.
 * Rubric windows and emergency gate patch protocols.
 * MAD-entropy and deadlock escalation to Meta Muse Spark.
 * KL drift check and canary tasks for model-swap detection.
### Phase 3: Advanced Ecosystem Integration
 * Full deployment of SAM 3.1 visual parsing pipelines.
 * Signal Watcher cross-agent learning loops.
 * Remaining task distributions: API misuse, edge cases, logic inversion.
 * Production hardening and multi-distribution stress testing suites.
## 18. Open Points
 * Topology Representation: Whether subagent topologies should be strictly graph-configured state machines or fully synthesized Python scripts.
 * Distance Metric Weights (w₁, w₂, w₃): Empirical calibration of tool profile vs. state path vs. embedding distance weights in the behavioral signature.
 * MAD Entropy Calibration: Empirical tuning parameters for the MAD entropy escalation threshold across different task domains, and the KL drift stability threshold (§10).
 * Window Length (N): Determining the optimal generation count for Rubric Windows under rapid vs. slow task distribution shifts.
 * Agent Spec Portability: Ensuring frozen Agent Specs can execute reliably across different underlying model version updates.
 * SAM 3.1 Output Evaluation: Defining standardized validation metrics for visual layout and workflow parsing outputs.
 * Ledger Merging: whether, and with which per-unit merge rules, parallel lineages should be merged after the MVP.
 * Model Availability: confirm API access, pricing and capabilities for Meta Muse Spark and Meta Muse Code. SAM-family models perform image segmentation; turning diagrams and workflows into structured data may need an additional model. Model IDs are set per role in config, so components do not depend on a specific provider.
## 19. One-Line Definition
Project Apex is a competitive evolutionary synthesis engine that generates verified, task-specialized autonomous agents by running parallel subagent populations over an immutable decision ledger governed by hard safety gates, evidence-backed causal attribution, and custodian-managed hidden holdouts.
